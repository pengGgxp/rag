- 文件与目录共用冲突检查，拒绝路径穿越、根目录破坏、移动到自身内部及跨工作区访问。

- 恢复失败保留状态及材料，不能报告成功，也不能在重试中破坏更新后的文件。

## 已确认取舍 A：OSS 与挂载直写的并发边界

用户已在承接对话明确回复“选 A”。保留 OSS 与当前挂载直写，不更换基础设施；平台 API 写入串行、保存前核对真实 revision，新建使用禁止覆盖。外部挂载写入与网页操作之间的并发窗口作为明确限制，不宣称原子替换或条件删除。按此决定恢复实施。

以下为选 A 之前的只读核对记录；用户确认后已经实施，当前实现和验收结果见后文。

- `shared_resources.backend` 当前共享工作区使用 OSS；`cloud_computer` 挂载相同 resource-directory 前缀。
- `OssStorage.put/delete` 目前无条件写/删；CopyObject 的 if_match 是源对象复制条件。
- 当前 OSS V2 SDK 的 PutObjectRequest 提供 forbid_overwrite，但没有目标对象 ETag 的条件替换参数；DeleteObjectRequest 也没有此条件删除参数。官方公开 API 同样未列出目标内容匹配后替换/删除能力。
- `cloud_file_operation.write_mounted` 直接写挂载路径；run_command 的普通脚本也可直接写文件，不参与 API 数据库行锁。
- 因而“网页检查旧 revision → 云电脑写新内容 → 网页无条件覆盖/回滚”存在竞态。平台数据库锁只能约束参与同一协议的写入，不能保护挂载任意直写。
- 临时备份只能提供补偿材料，不能消除竞态；本地内存适配器模拟条件写不能证明真实 OSS 支持此保证。

用户已选择保留当前 OSS 及挂载任意直写，并接受平台内串行、保存前 revision 检查仍存在上述并发窗口。无需再次确认，也不更换基础设施。
