# Issue #100：以真实文件发现 Skill 的设计梳理

日期：2026-11-14。状态：已按用户选择 A 实施并完成本地隔离验收，等待 PR #101 人工 review；实现、验证结果和真实 OSS/模型/云电脑的未验收边界见 `issue-100-skill-decoupling-implementation.md`。

## 目标、范围与边界

目标：平台仓库提供可复制的 Skill 包；工作区中的真实目录和 SKILL.md 决定已安装内容；模型通过元数据发现 Skill，再用现有文件/命令工具读取和执行。

范围：工作区 Skill 发现、平台安装判断、包的写入与删除、管理页元数据、模型上下文、必要回归。文件管理器外观保持当前已认可方案。

不包含：新 Skill 执行器、独立挂载、发布副本、正文同步、强制版本锁定、依赖预安装、语义依赖校验、第三方市场或收费模型/云电脑验收。

本项目目标目录使用用户本次指定的 `.skills/`。文件管理器应正常显示、进入和操作这个隐藏目录。这里不将 `.skills/` 声称为 Codex 的官方固定目录。

## 参考的 Codex 机制

可直接参考的是本对话已提供的 Codex 技能机制：先给名称、简介与 SKILL.md 位置，任务匹配后再读取具体说明。官方网页检索本轮未返回可引用正文，直接访问官方页面又遇到 403/超时，因此本稿不声称已核实 Codex 的全部内部实现。以下是本项目的设计建议：

- Skill 是包含 SKILL.md 的目录，可附带 scripts、references、assets。
- SKILL.md 的 YAML frontmatter 提供 name、description；模型先看元数据和路径，再在选用时读正文。
- 用户可显式指定 Skill，模型也可按 description 判断是否适用。
- 本项目同名 Skill 以具体路径区分，不合并或自动删除。
- 本项目采用用户指定的 `.skills/`，借鉴发现与按需读取机制。
- 实现“系统提示词注册”时，平台定义发现/使用规则，用户可编辑的元数据和正文须保持数据/用户指令边界，不得因为拼接进 system 消息就提升权限。

尝试核对的官方页面（本轮未取得正文）：

- `https://developers.openai.com/codex/skills/`
- `https://developers.openai.com/cookbook/examples/skills_in_api`

## 四层职责

| 层 | 负责 | 输入输出 |
| --- | --- | --- |
| 平台仓库 | 管理员维护源包；用户浏览、搜索、介绍、下载、复制到工作区 | 独立源包，不跟踪用户副本正文 |
| 工作区文件 | 保存安装/导入后的真实目录和文件，执行普通文件操作 | `.skills/<目录>/SKILL.md` 及同目录资源 |
| Skill 发现 | 在指定根目录中发现 SKILL.md，读取最小元数据 | name、description、manifest_path、directory |
| 模型运行 | 接收可用清单，按任务读取说明、资料、运行脚本 | 复用 read_file、run_command 等现有工具 |

管理页、平台“工作区已有”状态及模型可用清单复用同一个发现入口，避免三套不同的 Skill 状态。

允许使用可丢弃的文件索引/元数据缓存提速；缓存必须可以从当前文件重建，不拥有正文或独立的安装生命周期。

## 文件与元数据约定

```text
工作区/
└── .skills/
    └── report-helper/
        ├── SKILL.md
        ├── scripts/
        │   └── report.py
        ├── references/
        │   └── writing-guide.md
        └── assets/
            └── template.docx
```

```markdown
---
name: report-helper
description: 根据工作区资料整理报告；需要生成报告或复用报告模板时使用。
---

读取 references/writing-guide.md，按任务需要使用 assets/template.docx。
需要生成文件时，从本 Skill 目录运行 scripts/report.py。
```

规则：路径定位实际文件，name 表示 Skill 名称，description 说明用途与使用条件。名称取自 frontmatter，不从平台 ID 或安装记录推断。用户修改 name/description 后，下次发现读取新值；目录名变化仅改变路径。

发现只在指定 Skill 根目录内查找清单，支持导入包已经确定的嵌套目录，不把整个工作区里任意一份名为 SKILL.md 的资料都自动注册。找到一个 Skill 根后，不把它 references/assets 中的示例包继续当作独立 Skill 扫描。

元数据读取仅要求可读清单和可用的 name、description；失败时跳过该条模型注册，管理页在对应目录提示修复清单，文件照常可查看和编辑，其他 Skill 不受影响。

不比对平台源包与工作区副本的全部文件、脚本哈希、版本或资源清单。资源被修改、添加或移除，不会因与原包不同就被判定“未安装”。引用的文件不存在时，在真正使用该文件时报告。

## “已安装”的含义与安装流程

平台检查当前工作区发现结果：有可发现的 Skill 且其 frontmatter.name 与仓库包的 Skill 名称一致，就视为工作区已有该名称的 Skill，并返回实际目录供定位。

名称只用于发现/匹配，不证明来源或字节与平台包相同。外部导入的同名包也应显示为“工作区已有”；不冒充“经校验的官方副本”。同名不同目录的条目保留，列出路径区分，不合并或自动删除。

平台安装行为：

1. 当前工作区已有同名 Skill：返回已有目录，重复请求不再次创建、不覆盖。
2. 没有同名 Skill且目标目录不存在：将源包写入 `.skills/<包目录>/`，保留普通资源结构。
3. 目标目录已被其他内容占用：作为普通路径冲突处理，由用户选择保留/更名或取消，不擅自替换。
4. 写入过程复用工作区文件层的权限、并发冲突、幂等和失败恢复，不增加独立安装状态机。

工作区 A 和 B 各自扫描、各自写入，同名目录不跨工作区冲突。移除对 WorkspaceSkillInstall 作为安装事实来源的依赖；既有来源记录最多用于来源展示，不决定可用性、重装或运行权限。后续实现整理不再使用的表与调用，避免长期双轨判断。

## 目录和正文变化自然生效

| 用户操作 | 应有结果 |
| --- | --- |
| 删除 Skill 目录 | 下次发现移除该条；平台恢复可安装，允许重新安装 |
| 修改说明/脚本 | 下次读取直接使用当前字节；不从源包回填 |
| 修改 name/description | 下一轮清单使用新元数据；name 改变后按新名称参与仓库匹配 |
| 目录重命名或在 `.skills` 内移动 | 下次发现更新路径；name 未变则仍是同名 Skill |
| 将目录移出发现根 | 保留为普通工作区文件，不再自动加入可用 Skill 清单 |
| 手动创建合法 Skill 目录和清单 | 下次发现后出现在管理页与模型清单，无需额外注册按钮 |
| 同名 Skill 位于两个路径 | 两条都保留，以路径区分；仅点名且无法区分时由模型进一步确认 |

卸载复用普通工作区目录删除及其共享影响确认，不新增“数据库卸载后同步删文件”的第二条流程。

## 模型上下文与工具

每个用户消息开始时，服务端从当前有权限工作区的文件发现 Skill，生成本轮可用清单；普通工具循环不反复塞入完整正文。

示例数据：

```json
{
  "name": "report-helper",
  "description": "根据工作区资料整理报告；需要生成报告或复用报告模板时使用。",
  "path": ".skills/report-helper/SKILL.md"
}
```

平台提示规则告知：Skill 根目录、工作区路径基准、显式指定和按用途选用规则；使用前按清单 path 读取当前 SKILL.md，再按需读取相对参考文件或执行脚本。云电脑中的绝对路径由同一工作区挂载基准解析，不能拼出另一份文件副本。

用户控制的 name、description、path 使用结构化数据块提供，不拼成可任意改变平台规则的 system 指令。清单可在 system 消息中由平台规则引用，但用户可编辑字段应置于明确数据/用户上下文中；Skill 正文通过文件工具读取，不自动复制到 system 指令。

名称和简介只帮助选择，不能增加工具、权限或授权。用户明确要求优先于 Skill 指南。调用 read_file/run_command 后，仍执行既有工作区权限和费用规则；发现、注入摘要、普通发消息不启动云电脑。

会话续传、上下文压缩恢复及普通新消息都复用同一清单生成入口。删除或移动后，下一轮更新清单；同轮文件消失时按现有 404 处理，不能从旧快照恢复文件或绕过权限。

## 当前实现需要调整的关键点

- `ExtensionRuntime.skills` 当前默认空，除应用内功能外没有注册工作区元数据；接入发现结果。
- `agent.py` 和 `conversation_context.py` 已有 Skill 摘要入口，但须统一元数据结构、路径及指令优先级边界，所有模型请求路径都一致。
- `catalog/catalog_detail/catalog_install` 当前依赖 WorkspaceSkillInstall 并比较完整包文件清单；改为文件发现判断。
- 管理员导入目前剥离 frontmatter，将名称/简介单独存储，下载/安装又只写正文。必须统一包的导出构建，保证下载包和安装结果的 SKILL.md 包含 name、description；已有完整清单与平台编辑字段不能相互矛盾。
- 用户导入目录不再只用随机 UUID 作为用户看到的名称，应使用可读的包目录名称，冲突沿工作区文件规则处理。
- Skill“在工作区查看”定位发现到的真实目录；查看、编辑、删除复用同一文件操作。
- 修复此前审计的通用目录/文件问题，不能把移动失败、并发保存等包装成 Skill 专属校验。

## 历史路径处理

当前代码生成 `skills/<名称>-<平台ID>/` 或 `skills/<uuid>/`，此前需求也提到 `.skill/`；最新目标为 `.skills/`。这三者并非同一路径。

实现前盘点当前确有数据的路径及受影响范围。禁止因为改发现规则就自动移动、删除或公开用户历史文件；不设计永久扫描整个工作区或多套独立目录同步。本设计稿不执行迁移，迁移涉及真实业务文件时须按 Issue 的约定单独明确具体动作。

## 验收标准与后续实施顺序

1. 文件驱动：手动创建、改名、移入/移出、修改元数据、删除后，管理页与下一轮模型清单反映相同结果；同名不同路径不合并。
2. 安装闭环：A/B 工作区均可安装；重复安装不写入；修改任意资源仍视为已存在；删除后可重新安装；只看名称不声称来源一致。
3. 包一致：平台下载和安装得到同样的清单元数据与资源字节；外部文件夹/ZIP导入后可发现。
4. 模型使用：先看摘要，选中后read_file读取真实说明，相对资源及命令写入同一工作区；不强制新增 load_skill 工具或预加载全部正文。
5. 基础边界：viewer不能写，跨工作区隔离；路径穿越、链接、解包数量/大小、普通写入的并发保护与失败恢复照常。
6. 费用：发现、摘要注入、浏览、安装、普通消息均不创建云电脑；真实文件工具/执行按现行规则，付费真实验收另需明确预算。
7. 验证：先隔离文件发现/上下文/权限/幂等及失败回归，再本地临时Docker/账号/目录完整浏览器操作。模拟模型与真实模型结果分开记录。

实施顺序建议：统一清单与包格式 → 文件发现共用入口 → 仓库安装状态解耦 → 模型上下文接入 → 管理页真实目录操作 → 完整回归。现有工作区通用数据一致性缺陷仍优先于新增交互。
