# 支付 FM 积分充值

## 快捷金额与自定义金额（Issue #63）

2026-10-30：增加 20、50、100、200 元快捷选项和自定义金额，不修改配置中的套餐和兑换率。已有同金额套餐保留原价格、积分和标识；其余新增金额及自定义金额从现有套餐中最低积分／金额比例推导，不引入额外折扣，也不改变价格助手使用最优惠套餐的保守计算依据。

- `GET /payments/catalog` 保留 `packages`，增加 `custom`，包含允许范围、兑换分子分母、标识和报价指纹。仅在真实充值配置完整时提供。
- 自定义人民币金额通过 `custom_amount_fen` 传递，必须为严格整数分；通常范围 1–10000 元，最多两位小数，并根据现有充值积分上限收紧。不接受客户端积分、价格或状态。沿用充值订单整数积分，无法整除时向下兑换，支付前展示准确到账数；当前站点兑换率为每元 100 积分，任意有效分金额均可精确兑换。
- 自定义下单提交目录中的标识及报价指纹，后端核算金额和积分并固化订单。订单内部标识区分自定义金额；相同请求不同金额返回 409。订单已创建后即使目录停用或改价，原请求仍恢复原订单，回调按其原始金额和积分处理。
- 页面复用单选选项及原支付操作，提供本地合法性反馈、实时到账预览、提交禁用和失败保留输入。手机两列排列，支持方向键选档及 Tab 进入金额。恢复订单不自动再次向支付渠道下单。
- 验证：支付与定价助手 80 项回归通过；隔离 PostgreSQL 4 项并发回归通过，包含同一自定义请求并发 8 次只产生一个订单和一次渠道调用。Playwright 已检查 1440、700、390px、reduced motion、边界小数、网络失败、丢失下单响应的幂等恢复、503 输入保留、慢请求禁用、键盘和刷新恢复；截图在未跟踪 `output/playwright/recharge63-*`，已人工检查。
- 不新增数据库结构、不改 `.env`、既有套餐、消费价格或历史账单。浏览器验收使用隔离账号和不调用真实支付的测试替身；未执行真实付款，不能据此宣称新金额已完成支付渠道实付验收。

## 目标与范围

2026-10-22：根据用户指定的支付 FM 商户平台，新增积分充值闭环。
本次只做充值；保留现有积分账户、注册赠送、问答预扣和失败返还，不调整消费规则。
支付网关接入扩展了原功能基线中“不含支付网关”的边界。

- 账号中提供积分余额、服务端配置的充值档位、支付跳转、订单和积分流水。
- 订单固化工作区、付款用户、金额（整数分）、积分数量、商户和支付方式。
- 下单必须携带档位报价指纹；展示之后价格发生变化则拒绝下单，要求重新确认。
- 创建订单前持久化；网络异常不自动重复向网关下单。
- 回调校验签名、商户、订单、订单金额和已知平台订单号后，事务内入账。
- 行锁、订单唯一约束和流水幂等键防止重复回调、并发回调导致重复到账。
- 支付后返回页面只用于展示，不作为付款凭证；页面轮询本站订单，不轮询网关。
- 迟到的有效回调仍然入账，不能因为界面显示过期而吞掉已付款积分。
- 关闭所有客户的直接赠送积分接口。工作区管理员是客户，不是平台运营者。
- 积分仍归工作区共享；所有成员可为当前工作区付款，但只查看自己的充值订单。

## 不包含

- 充值之外的 Token/模型/工具计费规则管理、订阅、发票、退款或提现。
- 没有商户权限的主动查单接口；补单依赖商户后台重新通知。
- 脚本模拟的支付成功、浏览器传入金额或积分、客户 API 密钥管理。
- 擅自决定售价或积分兑换比例。

## 官方协议

- 创建订单：https://docs.zhifux.com/read/zhifufm/startorder
- 支付回调：https://docs.zhifux.com/read/zhifufm/notify
- 主动查单权限：https://docs.zhifux.com/read/zhifufm/querybyoutno

使用 `POST {接口根地址}/startOrder`，参数放 Query，响应为 JSON。
下单签名为 `md5(merchantNum + orderNo + amount + notifyUrl + secret)`。
回调签名为 `md5(state + merchantNum + orderNo + amount + secret)`。
签名使用回调原始金额字符串；另用整数分比较订单金额。
`actualPayAmount` 可能浮动且不在签名中，不用于兑换积分或替换订单金额。
回调的支付方式可能是轮循池实际分配的方式，不强制等于下单的池编码。
入账后才响应纯文本 `success`，失败响应 `fail`。

## 配置与上线条件

仅 API 服务持有接入密钥，配置在忽略提交的 `.env`，不进入前端。
默认不开启充值，也不预设商业售价。

- `ZHIFUX_ENABLED=true`
- `ZHIFUX_API_BASE_URL`：商户后台“用户中心 / API 开发信息”的接口根地址，不是登录地址。
- `ZHIFUX_MERCHANT_NUM`：商户号，不是登录账号。
- `ZHIFUX_SECRET`：接入密钥。
- `ZHIFUX_PAY_TYPE`：已在商户后台开通的支付产品/轮循池编码。
- `RECHARGE_PACKAGES_JSON`：档位数组，每项为 `id`、`name`、`amount_fen`、`credits`。
  `amount_fen` 是整数分，`credits` 是正整数；由运营者确认售价后填写。
- `API_PUBLIC_URL`：公网 HTTPS API 根地址，回调路径为 `/payments/zhifux/notify`。
- `FRONTEND_URL`：公网 HTTPS 网站根地址，付款后返回账号的充值页。

不打印密钥或带签名的请求 URL。网关必须使用 HTTPS，支付链接也必须使用 HTTPS。
更换商户或密钥前必须先处理旧订单，否则旧签名可能无法验证；本次不引入密钥轮换系统。
上线后回滚应用应保留新增订单表；已有真实订单时不要直接降级删除该表，先备份并核对账务。
公网反向代理应避免记录回调 Query 和带签名的请求，回调不能被登录/WAF 验证页或跳转拦截。
若支付成功未到账，应先在商户后台核对金额，再重新发送通知，不从前端手工标记成功。

## 验收与验证

1. 未配置时展示“暂未开放充值”，不显示虚构套餐、模拟收银台或配置细节。
2. 已配置时可以选档、创建订单、跳转收银台；刷新后仍能恢复自己的订单。
3. 普通客户及工作区管理员均不能直接增加余额；跨用户/跨工作区不能读取订单。
4. 篡改价格、积分、档位或幂等参数不能改变已创建订单的金额或到账积分。
5. 未登录、无效签名、非成功状态、错误商户/金额/平台单号、重复参数不能入账。
6. 重复/并发通知只增加一次余额；不同订单并发到账不丢失余额或累计值。
7. 超时/畸形响应不入账；回调早于下单响应、迟到回调、价格调整后回调均可靠。
8. 订单、积分流水和审计在同一事务提交；返回页面伪造成功参数不入账。
9. 单元/API 测试覆盖以上分支；PostgreSQL 验证迁移及并发；前端构建和桌面/手机浏览器验收。
10. 真实支付必须使用用户提供的商户配置、公网回调及已确认的售价进行人工付款验证。
