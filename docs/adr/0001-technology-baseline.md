# ADR-0001：技术基线与外部服务策略

- 状态：已确认
- 日期：2026-10-20
- 适用范围：RAG 平台初始实现

## 背景

平台需要在保持实现简单的同时，支持知识库导入、检索、问答、引用和持续维护。模型、Embedding 和登录方式都可能在后续更换，因此不能把业务逻辑直接绑定到单一供应商。

## 决策

### 应用架构

- 使用一个代码仓库。
- 使用模块化单体 API。
- 使用独立异步 Worker 处理文档解析、切分、Embedding 和索引任务。
- 本地开发和验证优先使用 Docker Compose。

### 前端与后端

- 前端使用 Next.js + TypeScript。
- UI 使用 Tailwind CSS 和轻量组件库。
- 后端使用 Python + FastAPI。
- 数据校验使用 Pydantic。
- 数据访问使用 SQLAlchemy。
- 数据库迁移使用 Alembic。

### 数据与检索

- 主数据库使用 PostgreSQL。
- 向量检索使用 pgvector。
- 关键词检索使用 PostgreSQL Full-Text Search。
- 默认采用向量检索与全文检索结合，再使用 RRF 融合。
- 原始文件使用 S3 兼容对象存储；本地开发使用 MinIO。

### 异步任务

- 使用 Redis 作为任务队列基础设施。
- 使用 Celery 运行异步 Worker。
- 文档处理任务必须支持状态、重试、取消、幂等和错误记录。

### 模型供应商

- 默认接入兼容 OpenAI API 的云端模型服务。
- 默认使用云端 Embedding 服务。
- 业务代码不得直接依赖某一家模型供应商的 SDK 或字段。
- LLM、Embedding、Parser、Retriever 和 Reranker 都必须通过适配器接口接入。
- 模型名称、API 地址、密钥和模型参数通过环境变量或安全配置注入。
- 密钥不得写入 Git、数据库明文或前端代码。

### 身份认证

- 同时支持网站本身的注册、登录和密码找回流程。
- 一开始接入 OAuth 登录。
- 本地账号和 OAuth 账号可以关联到同一个用户。
- 登录态使用安全的 HttpOnly Cookie。
- OAuth provider 通过适配器配置，避免把业务逻辑写死在单一 provider 上。

### 验证与发布

- 后端测试使用 pytest。
- 前端和关键用户流程使用 Playwright 验证。
- 使用 GitHub Actions 执行基础 CI。
- 初始目标是本地 Docker 可运行；云端部署作为后续部署目标，不提前引入云厂商专属基础设施。

## 不采用的方案

当前不引入：

- 微服务拆分
- Kafka 等重型消息系统
- 专用向量数据库
- GraphRAG
- 复杂企业级 IAM
- 将单一模型供应商 SDK 直接散落在业务代码中

## 结果与约束

- 这套方案优先保证本地可运行、开发可验证和后续可替换。
- PostgreSQL 同时承担业务数据、全文检索和初始向量检索，避免早期基础设施过重。
- 未来如果规模、延迟或合规要求变化，可以在不改变业务 API 的前提下替换向量库、对象存储、模型供应商或身份 provider。
