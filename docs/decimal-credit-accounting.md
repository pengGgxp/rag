# 实际用量与四位小数积分

关联 Issue：#57。目标是修复少量 Token 被凑满整单位收费，并统一余额、流水和待结算精度。
不调整商业单价、单位、倍率、充值兑换、默认模型或 Issue #36 开关，不重算历史消费及待结算金额。

## 结算规则

```text
精确费用 = Σ（实际用量 / 计价单位大小 × 单位积分价）× 工作区倍率
结算积分 = round_half_up(精确费用, 4)
```

全过程使用有理数，金额字段使用 `Numeric(24,4)`，不经过浮点累计。
模型整次请求合计后保留四位；OCR、Embedding 按现有结算事件保留四位。
明细使用最大余数法分配 0.0001 积分，合计与实际扣款严格一致。
推理 Token 已包含在输出时不重复相加；缓存开关关闭时仍按原输入总量计费，不启用缓存优惠。
没有可信 usage 的失败调用不估算扣款；已有快照、幂等、预授权返还和待结算继续有效。

真实记录示例：886 输入 × 1402/百万 + 47 输出 × 3804/百万 = 1.42096，
结算为 1.4210；2929 Embedding Token × 101/百万 = 0.2958。
这些数字用于复算，不写入或覆盖实际商业配置。

## 数据与页面

迁移 `0036_decimal_credits` 将账户、流水、消费、旧价和待结算金额改为定点数，
原整数金额数值不变。存在小数或超出整数范围时拒绝降级，避免悄悄损失余额。
充值套餐与注册赠送仍为整数，不改变兑换关系。
基准价、人工调整可输入四位小数；普通余额与消费最多显示四位，倍率预览不提前取整。
JSON 边界显式序列化数字或金额字符串，内部计费及数据库不使用浮点运算。
